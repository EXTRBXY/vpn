# ADR-0001. Привилегированная служба вместо повышения клиента

- Статус: принято (18.10.2026)
- Связано: [SECURITY.md](../SECURITY.md), [UPDATE-HANDOFF.md](../UPDATE-HANDOFF.md), [REFACTORING.md](../REFACTORING.md)

## Контекст

TUN-режим требует прав администратора. Сейчас клиент ради этого перезапускает **себя** через `runas --takeover` и
остаётся повышенным до выхода. Отсюда три проблемы:

1. **Повышение прав через каталог установки.** Приложение стоит в `%LOCALAPPDATA%\Programs\NothingVpn`
   (`PrivilegesRequired=lowest`), куда может писать любой процесс пользователя. Повышенный клиент запускает
   `sing-box.exe` и `wintun.dll` из этого каталога и сам повышается оттуда же. Подмена файла даёт чужому коду права
   администратора после привычного подтверждения UAC.
2. **Весь интерфейс работает от администратора** во время TUN-сессии: разбор подписок, HTTP, WPF.
3. **Сложное обновление.** Повышенный клиент не может просто запустить установщик: тот унаследовал бы права.
   Поэтому есть PowerShell-помощник, `WindowsUserProcessLauncher` и протокол `READY/COMMIT`
   (см. UPDATE-HANDOFF.md). После обновления клиент стартует без прав, и TUN нужно подключать заново.

## Рассмотренные варианты

| Вариант | Итог |
| --- | --- |
| А. Проверять хеши `sing-box.exe`/`wintun.dll` | Не закрывает подмену самого `NothingVpn.Desktop.Wpf.exe` |
| Б. Установка в `Program Files`, клиент по-прежнему повышается | Закрывает подмену, но интерфейс остаётся повышенным, обновление остаётся сложным |
| **В. Служба Windows управляет sing-box, интерфейс никогда не повышен** | Закрывает все три проблемы. Принято |

## Решение

### Компоненты

- **`NothingVpn.Service`** — служба Windows (LocalSystem, автозапуск) в `%ProgramFiles%\NothingVpn`. Единственный
  процесс, который запускает `sing-box`. Использует `ProcessJobScope`, ищет `sing-box.exe` и `wintun.dll` **только**
  в своём каталоге установки (без поиска по `bin\` и родительским каталогам).
- **Интерфейс** (`NothingVpn.Desktop.Wpf`) работает только с правами пользователя. Хранит профили, подписки и
  настройки в `%LOCALAPPDATA%\NothingVpn.Tray` под DPAPI CurrentUser, как сейчас. UAC-перезапуск (`--takeover`)
  удаляется.
- **Все режимы — через службу**, включая `proxy`: один путь кода для запуска ядра. Системный прокси WinINET хранится
  в `HKCU`, поэтому его по-прежнему включает и восстанавливает интерфейс; служба лишь поднимает `mixed`-inbound
  на `127.0.0.1`.

### Канал и протокол

- Именованный канал `NothingVpn.Service` с ACL: полный доступ SYSTEM и администраторам; чтение и запись —
  интерактивным пользователям (`INTERACTIVE`). Сетевой доступ к каналу запрещён.
- Служба занимает имя канала с `FILE_FLAG_FIRST_PIPE_INSTANCE`, клиент до отправки первого сообщения проверяет, что
  сервер канала — служба от LocalSystem (подробно — «Протокол канала» в шаге 7а). Иначе процесс пользователя,
  занявший имя раньше службы, получил бы UUID и ключи профиля.
- Сообщения — JSON с версией протокола; несовместимая версия отклоняется понятной ошибкой («обновите приложение»).
- Команды: `Connect(request)`, `Disconnect`, `GetStatus`, `SubscribeLog`. События: изменение состояния, строки
  журнала (журнал маскируется в службе через `LogRedactor`).
- **Служба не принимает готовый JSON sing-box.** В конфигурации sing-box есть поля с путями к файлам; принятый от
  пользователя конфиг дал бы запись от имени SYSTEM в произвольные места. Запрос `Connect` — типизированный:
  параметры профиля VLESS, режим, DNS-, TUN-, proxy-настройки, пути `.exe` для `tun_apps`, rule-set. Служба
  валидирует его Domain-политиками и сама строит конфигурацию тем же генератором.
- **Rule-set передаются содержимым** (с ограничением размера), а не путями к файлам пользователя. Служба кладёт их в
  `%ProgramData%\NothingVpn\rulesets` (ACL: SYSTEM и администраторы). Там же — временные конфиги.
- Время жизни VPN управляется явно: выход из интерфейса отправляет `Disconnect` (как сейчас). Если интерфейс упал,
  служба продолжает работу, а перезапущенный интерфейс узнаёт состояние через `GetStatus`.

### Обновление

- Интерфейс без прав скачивает установщик и запускает его; установщик (`PrivilegesRequired=admin`) сам запрашивает
  UAC. Установщик останавливает службу, заменяет файлы, запускает службу.
- После установки интерфейс запускается от имени исходного пользователя (`runasoriginaluser` в `[Run]`).
- `WindowsUserProcessLauncher`, `InstallerUpdateWorker` и протокол `READY/COMMIT` удаляются: интерфейс больше
  никогда не бывает повышен, наследовать нечего.
- Обновление без UAC силами самой службы **не делаем**: служба от SYSTEM, запускающая неподписанный файл из сети,
  опаснее текущего положения. Это возможно только вместе с проверкой подписи. Подпись обновлений отложена
  (решение 18.10.2026: узкий круг пользователей, GitHub-аккаунт под двухфакторной аутентификацией).

### Установка

- Inno Setup: `PrivilegesRequired=admin`, `DefaultDirName={autopf}\NothingVpn`, регистрация и запуск службы,
  остановка и удаление службы при деинсталляции. `AppId` прежний.
- Новый установщик находит старую per-user установку (`HKCU\...\Uninstall\{A2D610D2-…}_is1`), удаляет её тихо
  **с сохранением данных** и переносит автозапуск `HKCU\...\Run\NothingVpn` на новый путь. Как именно — «Шаг 7б».
- Каталог данных `%LOCALAPPDATA%\NothingVpn.Tray` не меняется.

## Переход со старых версий

Клиенты ≤ 0.6.8 запускают установщик через свой помощник с `UseShellExecute=false`.

**Проверено 18.10.2026:** установщик Inno Setup 6 с `PrivilegesRequired=admin` имеет в манифесте
`requestedExecutionLevel="asInvoker"` и сам перезапускает себя с запросом UAC. Значит, старый клиент, скорее
всего, сможет запустить новый установщик без изменений.

**Проверено вручную 19.10.2026 (шаг 7в, эмуляция):** установщик со службой, запущенный так же, как его запускает
0.6.8 (процесс без прав, `UseShellExecute=false`, `/SILENT /SP- /SUPPRESSMSGBOXES /CLOSEAPPLICATIONS /NORESTART`),
показал UAC и после подтверждения установился до конца: служба запущена, per-user копия удалена, данные и настройки
целы, интерфейс запустился без прав, подключение во всех режимах работает без UAC. **Решение: промежуточный релиз не
нужен.** Не проверено: запуск из 0.6.8, перед этим подключённой в TUN (повышенной), и настоящее обновление через
GitHub — это делается после публикации релиза со службой (чек-лист, раздел 7в-Б).

Шаг 8 этот переход не затрагивает: обновление с 0.6.8 запускает код самого 0.6.8, а установщик не менялся.
Новый путь запуска (без помощника) касается только обновлений с версий со службой.

План:

1. Собрать тестовый per-machine установщик и вручную обновить на него установленный 0.6.8 через встроенное
   обновление, в обычном и в повышенном (после TUN) клиенте.
2. Если проверка прошла — промежуточный релиз не нужен.
3. Если нет — выпустить **промежуточный релиз** (последний per-user), который запускает установщик так, чтобы
   Windows показала UAC (ShellExecute из процесса с обычными правами). Права передаются только через явное
   согласие пользователя в UAC, а не через наследование. Затем выпускать версию со службой.

## Последствия

- Плюсы: закрыт путь повышения через пользовательский каталог; интерфейс никогда не повышен; нет UAC при каждом
  TUN-подключении; удаляется самый хрупкий код обновления; VPN переживает падение интерфейса.
- Минусы: установка и каждое обновление требуют UAC; новый проект и протокол; на машине с несколькими
  пользователями VPN один на всех (кто подключил — то и работает; управлять может любой интерактивный пользователь).
- Тестирование: протокол канала и валидацию запроса покрыть unit-тестами; службу — интеграционным тестом с
  поддельным ядром; установку и обновление — ручным чек-листом.

### Шаг 6 — граница «интерфейс ↔ ядро» (сделано, 19.10.2026)

- Порт `IVpnEngine` (`src/NothingVpn.Application/Engine/`): `ConnectAsync(EngineConnectRequest)`, `DisconnectAsync`,
  `GetStatus`, событие `StatusChanged(EngineStatus)`. Это команды `Connect`/`Disconnect`/`GetStatus` и событие
  состояния канала.
- `EngineConnectRequest` и `EngineStatus` — сериализуемые System.Text.Json, имена JSON зафиксированы
  (`[JsonPropertyName]`), строки enum'ов те же, что в state.json. Версия — `EngineContract.Version = 1`, есть в каждом
  запросе и статусе; ядро отклоняет несовпадение ошибкой «Обновите приложение». Roundtrip покрыт `EngineContractTests`.
- Реализация внутри процесса — `SingBoxVpnEngine`: валидирует запрос Domain-политиками и `AppStateNormalizer`
  (не доверяя нормализации интерфейса), строит конфиг тем же `SingBoxConfigGenerator`, запускает sing-box через
  `ISingBoxPort`. Этот же класс будет ядром службы на шаге 7 — с её реализациями портов.
- Клиентская часть — `VpnConnectionService`: загрузка профиля и state.json, построение запроса, UAC-перезапуск (пока),
  WinINET и runtime-флаги, восстановление после остановки ядра, откат.

Уточнения протокола по итогам шага 6:

- **`SubscribeLog` — забота транспорта, а не порта.** Ядро пишет журнал в `ILogPort`; внутри процесса это общий
  буфер. Клиент канала на шаге 7 подписывается на журнал службы и записывает строки в `ILogPort` интерфейса, поэтому
  в `IVpnEngine` отдельной подписки нет. Сообщение `Log` канала: уровень, источник, текст (уже замаскированный).
- **`ProxyOverride` в запрос не входит**: список исключений нужен только WinINET, а его включает интерфейс.
  Порт mixed-inbound входит — служба поднимает inbound, интерфейс направляет на него прокси.
- **Rule-set пока передаются ссылкой**: `EngineRuleSet` содержит tag, действие и простое имя `.srs` (без пути, проверяет
  `RuleSetPolicyValidator`) в каталоге rule-set ядра; внутри процесса это общий `rulesets\` пользователя, и итоговый
  конфиг не меняется. Передавать содержимое сейчас значило бы копировать файлы при каждом подключении и менять пути
  в конфиге без пользы до появления службы. **TODO (шаг 7):** добавить в `EngineRuleSet` содержимое с ограничением
  размера, служба кладёт его в `%ProgramData%\NothingVpn\rulesets` под своим именем файла; версия контракта → 2.
  Сделано на шаге 7а.
- Статус ядра содержит режим и Id профиля работающей сессии — по ним перезапущенный интерфейс восстанавливает
  отображение после `GetStatus`.
- Проверка прав для TUN пока остаётся в интерфейсе (`VpnConnectionService` → `--takeover`); удаляется на шаге 8
  (сделано: теперь ошибка без перезапуска).

### Шаг 7а — служба и транспорт по каналу (сделано, 19.10.2026)

- **`src/NothingVpn.Service`** — exe службы Windows (`ServiceBase`, имя службы `NothingVpn`), self-contained
  single-file. `Build.ps1 -Target Publish` кладёт его рядом с клиентом в `artifacts\publish\win-x64`, в установщик он
  пока не входит. Запускается только диспетчером служб (консольного режима нет: владельцем канала может быть только
  SYSTEM, см. ниже). Composition root службы — `Infrastructure/ServiceHost/ServiceEngineHost`: тот же
  `SingBoxVpnEngine`, что внутри клиента, но с портами службы:
  - `SingBoxRunner.ForInstallDirectory` — `sing-box.exe` (а через рабочий каталог и `wintun.dll`) только из каталога
    exe службы, без `bin\`, родительских каталогов и `%LOCALAPPDATA%\Programs`;
  - каталог данных `%ProgramData%\NothingVpn` (`configs\`, `rulesets\`) с защищённым ACL — SYSTEM и администраторы,
    без наследования (`ServiceDataDirectory`);
  - свой `InMemoryLogStore`: вывод sing-box и сообщения службы маскируются `LogRedactor` при записи, в канал уходят
    уже замаскированные строки.
- **Клиент** — `Infrastructure/ServiceChannel/PipeVpnEngine` (`IVpnEngine`). Реализацию выбирает
  `ApplicationServicesFactory`: по умолчанию `SingBoxVpnEngine` внутри процесса; канал службы — только при переменной
  окружения `NOTHINGVPN_ENGINE=service` (режим разработки). Тогда при старте клиент до 3 с ждёт состояние службы
  (`RefreshStatusAsync`), недоступная служба пишется в журнал и не мешает запуску. UAC-перезапуск для TUN остаётся до
  шага 8 и в этом режиме.
- **Контракт v2**: `EngineRuleSet.Content` — содержимое `.srs` (в JSON — base64), не больше
  `RuleSetPolicyValidator.MaxContentBytes` (8 МиБ на файл) и `MaxTotalContentBytes` (16 МиБ на запрос).
  `VpnConnectionService` по-прежнему строит запрос без содержимого; его дописывает `PipeVpnEngine`, читая файлы с
  безопасным простым именем из `rulesets\` пользователя. Ядро получает файлы через порт `IEngineRuleSetStore`:
  внутри процесса — `ReferencedRuleSetStore` (имя из запроса в общем каталоге; итоговый JSON sing-box не изменился,
  эталоны прежние), в службе — `ServiceRuleSetStore`: запрос без содержимого отклоняется, файлы пишутся в
  `%ProgramData%\NothingVpn\rulesets` под именем `NN-<sha256>.srs` и удаляются при остановке. Конфиг службы отличается
  от конфига внутри процесса только путями `route.rule_set[].path`
  (`ServiceChannelTests.ServiceConfig_DiffersFromInProcessOnlyInRuleSetPaths`).

#### Протокол канала

- **Канал** `\\.\pipe\NothingVpn.Service`, байтовый режим, до 8 одновременных соединений. В одном соединении идут и
  запросы клиента, и события службы; клиент держит его открытым, пока работает.
- **Кадр**: 4 байта длины тела (uint32, little-endian) и UTF-8 JSON. Длина 0 или больше `MaxFrameBytes` (24 МиБ —
  с запасом на 16 МиБ rule-set в base64), обрезанный кадр, некорректный JSON или сообщение без `type` — нарушение
  протокола: служба отвечает `error` с кодом `protocol` без `id` и закрывает соединение. Тело должно прийти за 30 с
  после заголовка; ожидание заголовка не ограничено (соединение-подписка простаивает).
- **Сообщение** (`ServiceMessage`): `contractVersion`, `type`, `id` (у запросов и ответов) и нагрузка — `request`
  (`EngineConnectRequest`), `status` (`EngineStatus`), `error` (`code`, `message`) или `log` (`timestampUtc`, `level`
  со строками уровней как в state.json, `source`, `message`). Пустые поля не пишутся. Поля `contractVersion`, `type`,
  `id`, `error` не меняются между версиями — по ним любая версия распознаёт собеседника другой версии.
- **Версия**: `contractVersion` в каждом сообщении равен `EngineContract.Version` (сейчас 2). На чужую версию служба
  отвечает `error` с кодом `version` и текстом «Несовместимая версия протокола ядра (…). Обновите приложение.» и
  закрывает соединение; клиент, получив событие чужой версии, завершает запросы той же ошибкой.
- **Команды** (клиент → служба; ответ — `result` со `status` или `error` с тем же `id`):

  | `type` | Нагрузка | Ответ |
  | --- | --- | --- |
  | `connect` | `request` | статус после запуска; ошибка ядра — `error`/`failed` с текстом для пользователя |
  | `disconnect` | — | статус после остановки |
  | `getStatus` | — | текущий статус |
  | `subscribeLog` | — | текущий статус; затем текущий буфер журнала службы и новые строки событиями `log` |
  | другой | — | `error`/`protocol`, соединение остаётся |

  Команды одного соединения выполняются параллельно его чтению; взаимоисключение операций — внутри ядра.
- **События** (служба → клиент, без `id`): `status` — любое изменение состояния ядра, всем соединениям (в том числе
  неожиданный выход sing-box); `log` и `logCleared` (буфер очищен при старте sing-box) — подписанным. Очередь строк
  журнала на соединение — 2048 записей (при переполнении отбрасываются старые); кадр, который клиент не принял за
  10 с, закрывает соединение.
- **Тайм-ауты клиента**: подключение к каналу 2 с («Служба Nothing VPN не отвечает…»), `connect` 60 с, остальные
  команды 15 с. При обрыве ожидающие запросы завершаются ошибкой «Связь со службой Nothing VPN потеряна», клиент
  делает 3 попытки переподключения и снова подписывается на журнал; не вышло — считает ядро остановленным (sing-box
  привязан к Job Object службы и без неё не работает) и поднимает `StatusChanged`.

#### Безопасность канала

- **ACL** (`ServicePipeSecurity`): SYSTEM и `BUILTIN\Administrators` — полный доступ; `INTERACTIVE` — `ReadWrite`
  без `CreateNewInstance`, `ChangePermissions` и `TakeOwnership`; `NETWORK` — запрет; наследование отключено;
  владелец — SYSTEM.
- **Имя канала**: сервер создаёт первый экземпляр с `FILE_FLAG_FIRST_PIPE_INSTANCE` (имя занято — служба не стартует
  и пишет событие в журнал Windows) и не отпускает имя: следующий экземпляр создаётся до обработки подключённого
  клиента, а флаг ставится всякий раз, когда своих экземпляров не осталось.
- **Проверка сервера клиентом** (`LocalSystemPipeServerVerifier`) — до отправки первого байта; отказ —
  `ServiceAuthenticationException`, соединение закрывается, данные не отправлены. Задумывалась как проверка SID
  токена процесса сервера (`GetNamedPipeServerProcessId`), но проверено 19.10.2026 на Windows 11: процесс без прав
  администратора не может открыть процесс службы SYSTEM даже с `PROCESS_QUERY_LIMITED_INFORMATION` (ошибка 5), а
  `WTSEnumerateProcessesEx` не отдаёт ему SID. Поэтому проверка составная:
  1. владелец объекта канала — SYSTEM. Служба задаёт его явно; процесс без `SeRestorePrivilege` не может назначить
     владельцем SID, которого нет в его токене;
  2. сервер работает в сеансе 0 (`GetNamedPipeServerSessionId`) — сеансе служб;
  3. процесс сервера (`GetNamedPipeServerProcessId`): если его токен удаётся открыть (сервер — процесс того же
     пользователя, или клиент повышен), пользователь токена обязан быть LocalSystem.
- **Запрос**: служба не принимает готовый JSON sing-box и пути для записи — только `EngineConnectRequest`, который
  `SingBoxVpnEngine` валидирует Domain-политиками; имена rule-set из запроса в пути службы не попадают.
- Администратор машины может всё (в том числе остановить службу и занять имя) — это вне модели угроз.

#### Тесты

`ServiceProtocolTests` — кадры, версия, пределы, некорректный ввод. `ServiceChannelTests` — сервер и клиент в одном
процессе с поддельным sing-box: connect/disconnect/статус/журнал, ошибки ядра, старая версия клиента, неверный кадр,
обрыв и переподключение, rule-set содержимым, отказ проверки сервера без отправки данных (в том числе настоящая
проверка против сервера, созданного процессом пользователя), ACL канала и каталога данных,
`FILE_FLAG_FIRST_PIPE_INSTANCE`, поиск sing-box службой, выбор реализации ядра. Служба в тестах не устанавливается;
в тестах канал создаётся от текущего пользователя, поэтому положительный путь проверки сервера подменяется
внутренним интерфейсом `IPipeServerVerifier`.


Известное ограничение: Infrastructure по-прежнему зависит от WinForms (REFACTORING.md 3.6), и exe службы несёт
WindowsDesktop runtime (~72 МБ со сжатием single-file). Уйдёт с шагом 9.

### Шаг 7б — установка и интерфейс через службу (сделано, 19.10.2026)

#### Установщик (`build/installer/NothingVpn.iss`)

- `PrivilegesRequired=admin`, `DefaultDirName={autopf}\NothingVpn` (`C:\Program Files\NothingVpn`), `AppId` прежний.
  `DisableDirPage=yes` и `UsePreviousAppDir=no`: служба от SYSTEM запускает файлы из `{app}`, поэтому каталог только
  в Program Files — ни выбранный пользователем, ни прежний `%LOCALAPPDATA%\Programs\NothingVpn`. Манифест установщика
  — `asInvoker` (проверено на собранном `NothingVpnSetup.exe`): неповышенный процесс запускает его, Setup сам
  запрашивает UAC.
- Ставит `NothingVpn.Desktop.Wpf.exe`, `NothingVpn.Service.exe`, `sing-box.exe`, `wintun.dll` (и `*.pdb` клиента).
- **Служба `NothingVpn`** (имя — из `NothingVpnWindowsService.Name`; канал — `NothingVpn.Service`): после замены
  файлов `sc create` или, если уже есть, `sc config` — путь в кавычках, `start= auto`, `obj= LocalSystem`, отображаемое
  имя «Nothing VPN», описание; `sc failure … reset= 86400 actions= restart/5000/restart/10000/restart/60000` и
  `sc failureflag 1` (перезапуск и при остановке с кодом ошибки, например когда имя канала занято). Затем запуск
  с ожиданием `RUNNING` до 30 с. Отказ регистрации или запуска — сообщение (подавляется в тихом режиме) и запись в
  журнал установки; установка не откатывается.
- **Обновление**: `PrepareToInstall` (до проверки занятых файлов) останавливает службу, ждёт `STOPPED` до 30 с и
  выхода её процесса до 15 с; не остановилась — установка прерывается с понятным текстом. sing-box останавливается
  вместе со службой (Job Object).
- **Ярлыки** — для всех пользователей (`{group}`, `{autodesktop}`). Программа и служба ставятся на машину; при UAC
  от другого администратора (over-the-shoulder) личные папки установщика — это профиль администратора, и ярлыки
  достались бы не тому пользователю.
- **`[Run]`**: интерфейс — `postinstall nowait runasoriginaluser`, без `skipifsilent` (тихое обновление снова
  открывает интерфейс, как раньше). Если Setup запустили уже повышенным («Запуск от имени администратора»),
  исходный пользователь и есть повышенный — это ограничение Windows; интерфейс в таком случае повышен до перезапуска.
- **Деинсталляция**: остановка службы, `DeleteService`, удаление источника журнала событий `NothingVpn`, удаление
  `HKCU\...\Run\NothingVpn` у пользователя, который удаляет (если значение указывает на `{app}`), затем
  `%ProgramData%\NothingVpn`. Вопрос об удалении `%LOCALAPPDATA%\NothingVpn.Tray` — как раньше; тихая деинсталляция
  удаляет его без вопроса, как раньше. Каталоги удаляются без захода внутрь ссылок; дополнительно Inno Setup 6.7
  включает RedirectionGuard. Профиль — того, кто запустил деинсталляцию (HKCU и данные других пользователей
  деинсталлятору недоступны).
- `SetupLogging=yes`: журнал `%TEMP%\Setup Log *.txt` (у пользователя, подтвердившего UAC).

#### Переход со старой per-user установки

Старый деинсталлятор (`unins000.exe` из ≤ 0.6.8) **не запускается**: в тихом режиме его `InitializeUninstall`
ставит `UninstallRemoveUserData = True` и удаляет `%LOCALAPPDATA%\NothingVpn.Tray`. Вместо него после запуска службы
установщик вызывает `ExecAsOriginalUser("{app}\NothingVpn.Service.exe", "--migrate-user-install [--autorun]")` —
процесс с правами исходного пользователя (`Infrastructure/Installation/LegacyUserInstallMigration`):

1. Читает `HKCU\...\Uninstall\{A2D610D2-2A69-4D7A-9B06-6C0B4E5F5C87}_is1` (`Inno Setup: App Path`/`InstallLocation`,
   `UninstallString`, `Inno Setup: Icon Group`).
2. В каталоге старой установки удаляет **только известные файлы**: `NothingVpn.Desktop.Wpf.exe`, `NothingVpn.Tray.exe`,
   `sing-box.exe`, `wintun.dll`, `wpf-smoke-error.txt`, `NothingVpn*.pdb`, деинсталлятор `uninsNNN.exe` (только из
   этого каталога) с его `.dat`/`.msg`; каталог удаляется, только если опустел. Каталог, совпадающий с новым, не
   трогается. Рекурсивного удаления нет — путь в HKCU записывает пользователь.
3. Удаляет ярлыки старой копии: `Nothing VPN.lnk` и `Uninstall Nothing VPN.lnk` в личной группе меню «Пуск»
   (группа пустая — удаляется), `Nothing VPN.lnk` на личном рабочем столе.
4. Удаляет запись деинсталляции — даже если часть файлов занята: старый деинсталлятор, оставшись в «Программах»,
   предложил бы удалить данные.
5. Если `HKCU\...\Run\NothingVpn` уже был или выбрана задача «autorun» — записывает `"C:\Program Files\NothingVpn\NothingVpn.Desktop.Wpf.exe"`.

Каталог данных `%LOCALAPPDATA%\NothingVpn.Tray` не затрагивается ни в одной ветке. Код возврата (0 — всё удалено,
2 — остались занятые файлы, 1 — ошибка) пишется в журнал установки, установку не прерывает.

Почему от имени исходного пользователя, а не из повышенного [Code]: (1) при UAC от другого администратора HKCU
повышенного установщика — профиль администратора, и старую копию пользователя было бы не найти; (2) удалять с
правами администратора файлы по пути из пользовательского HKCU — примитив удаления в чужих каталогах. Ограничение:
если Setup запущен уже повышенным (не самоповышение), исходный пользователь — повышенный; при over-the-shoulder
вручную через «Запуск от имени администратора» миграция пройдёт в профиле администратора, и старую копию
пользователя нужно удалить вручную (её деинсталлятор с ответом «Да — оставить папку»).

#### Интерфейс через службу

- **Выбор ядра** (`ApplicationServicesFactory`): по умолчанию `PipeVpnEngine`; `SingBoxVpnEngine` в процессе — только
  при `NOTHINGVPN_ENGINE=inprocess` (разработка без установленной службы). Другие значения — служба: опечатка не
  переводит ядро в процесс интерфейса. Отката на ядро в процессе при недоступной службе нет: ошибка «Служба Nothing VPN
  не отвечает. Запустите службу «Nothing VPN» (services.msc) или переустановите приложение.», «Нет доступа к службе…»
  или `ServiceAuthenticationException` показывается при подключении.
- **TUN без UAC**: `IVpnEngine.TunRequiresElevatedCaller` — `false` у `PipeVpnEngine`, `true` у `SingBoxVpnEngine`;
  `VpnConnectionService` запрашивал `--takeover` только во втором случае. Код UAC-перезапуска и UPDATE-HANDOFF
  оставался до шага 8 (удалён, см. «Шаг 8»).
- **Старт и перезапуск интерфейса** при работающем VPN: `RefreshStatusAsync` (до 3 с) до `RecoverStaleRuntimeState`;
  работающая сессия службы не застряла — флаги WinINET в state.json и включённый прокси остаются. `GetStatus` без
  своей сессии берёт режим и профиль из `EngineStatus`, событие «работает» без своей сессии поднимает
  `ConnectionStateChanged(true)`. Отключение восстанавливает прокси по флагам state.json. Если служба при старте не
  ответила за 3 с, ядро считается остановленным и прокси восстанавливается: служба недоступна — значит, её sing-box не
  работает (Job Object).
- **Обновление из интерфейса** (до шага 8; новый путь — «Шаг 8») — прежний путь (`InstallerLaunchService` → помощник PowerShell →
  `Process.Start(UseShellExecute=false)` с `/SILENT /SP- /SUPPRESSMSGBOXES /CLOSEAPPLICATIONS /NORESTART`). Клиент
  неповышен, поэтому `WindowsUserProcessLauncher` запускает помощника с тем же токеном; установщик `asInvoker`
  стартует и сам запрашивает UAC. Ручная проверка — появится ли UAC в тихом режиме и пройдёт ли установка до
  запуска интерфейса — в чек-листе.

#### Каталог данных службы

`%ProgramData%` позволяет любому пользователю создать подкаталог. Созданный заранее `%ProgramData%\NothingVpn`
остался бы во владении пользователя (владелец может вернуть себе доступ после смены ACL) или был бы ссылкой — и
пользователь подменял бы конфиг, который sing-box читает от SYSTEM. `ServiceDataDirectory.EnsureTrustedDirectory`
принимает каталог, только если его владелец — SYSTEM или администраторы и это не точка повторной обработки; иначе
переименовывает его (переименование ссылки не трогает её цель), пытается удалить и создаёт новый сразу с защищённым
ACL (без окна с унаследованными правами). Не вышло — служба не стартует.

#### Тесты

`VpnConnectionServiceTests` (поддельное ядро службы: TUN без повышения, перезапуск интерфейса при работающей сессии,
событие «работает» без сессии, остановка службы), `LegacyUserInstallMigrationTests` (миграция: только известные
файлы, данные пользователя целы, путь из HKCU на чужой каталог, новый каталог не трогается, автозапуск; каталог
данных службы), `ServiceChannelTests.EngineSelection_DefaultsToService`. Установщик, служба и обновление — ручной
[чек-лист](../SERVICE-INSTALL-CHECKLIST.md).

### Шаг 8 — удаление повышения клиента (сделано, 19.10.2026)

Интерфейс с шага 7б не повышается, поэтому удалено всё, что существовало ради повышенного клиента.

- **UAC-перезапуск**: аргумент `--takeover` (теперь игнорируется) и ожидание мьютекса в `SingleInstance.Acquire`,
  `ConnectResult.RequiresElevation`/`ElevationArgs`, `ConnectionStartOutcome.ExitCurrentProcess`,
  `IAppLifecycleService`/`AppLifecycleService`, `StartupArguments`, `IElevationPort.RestartElevated` и
  `Elevation.RestartElevated` (`runas`). `IElevationPort.IsAdministrator` остался — для строки статуса и проверки
  ниже. `ConnectionController.StartAsync` больше не принимает режим (он нужен был только для аргументов перезапуска).
- **Ядро в процессе** (`NOTHINGVPN_ENGINE=inprocess`, разработка): TUN без прав администратора отклоняется ошибкой
  «Ядро в процессе: для TUN запустите клиент от имени администратора.» до обращения к ядру; клиент разработчик сам
  запускает от имени администратора ([DEVELOPMENT.md](../../DEVELOPMENT.md)).
- **Обновление**: `WindowsUserProcessLauncher`, `InstallerUpdateWorker` (помощник PowerShell), протокол
  `READY/COMMIT/COMMITTED` и его канал удалены вместе с `WindowsUpdateHandoffTests` и
  `build/Test-UpdateHandoff.ps1`. Новый `InstallerLaunchService`: `Prepare` до выхода (процесс не повышен, имя файла
  по `InstallerFilePolicy`, файл существует), затем штатный выход клиента (VPN отключён, мьютекс освобождён), затем
  `Launch` — `Process.Start` с `UseShellExecute=false`, тихими аргументами в `ArgumentList` и без переменных
  `NOTHINGVPN_*`. Повышенный процесс клиента (запущен «от имени администратора») обновление не запускает: установщик
  унаследовал бы его права. Установщик запускается после освобождения мьютекса, потому что это `AppMutex`
  установщика, а в тихом режиме Inno не ждёт закрытия приложения, а прерывается
  ([UPDATE-HANDOFF.md](../UPDATE-HANDOFF.md)).
- **`NothingVpn.Tray`** адаптирован минимально (запуск установщика после `Application.Run` и освобождения мьютекса),
  удаляется на шаге 9.

Ручная проверка — [чек-лист, раздел 7](../SERVICE-INSTALL-CHECKLIST.md#7-обновление-из-интерфейса). Тесты:
`InstallerLaunchServiceTests`, `UpdateViewModelTests` (порядок «проверки → выход → запуск»),
`VpnConnectionServiceTests.ConnectAsync_InProcessEngineTunWithoutAdmin_FailsWithoutStartingOrRestarting`.
